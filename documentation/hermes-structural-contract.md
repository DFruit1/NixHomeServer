# Hermes structural workflow contract

The owner authorized this work on 2026-10-23. It completes the fleet
simplification without changing credential, exposure, destructive-operation,
resource or NixOS deployment gates.

## Implementation and acceptance

1. Extend the existing native create, review and completion operations with
   validated structured inputs. Store new task contracts in their immutable
   creation event; retain existing body/comment contracts for legacy tasks.
   Generate readable markers from the structured contract. A structured delivery
   completion must bind current tracker scope and actual independent evidence;
   it must not turn routing or implementation into acceptance.
2. Exercise the installed tool transport, hooks and lifecycle in the existing
   confined synthetic fixture. Include rejection/rework, stale evidence,
   interrupted recovery and a mismatched source checkout.
3. Extend the existing dispatch policy to check declared execution prerequisites
   before launch and after workspace preparation. Keep independent review skills,
   native retry/provider budgets, active writers and reserved gates intact.
4. Reconcile detector observations against one original failure episode and
   recovery owner. A completed controller is not proof the original task
   recovered. Preserve all prior failed attempts and bounded backoff.
5. Make fleet releases declare file ownership and compose their maintained
   transforms. Refuse legacy cadence resurrection after migration; preserve
   existing schedules/history and verify clean install, upgrade and rollback.
6. Extend existing local reports with read-only outcome measurements: repeated
   incidents, maintenance effort and unfinished requested delivery. Unknown cost
   remains unknown. Do not add a monitor, role or model call.

Python is retained because these are native Hermes runtime and installer
extensions, sharing its existing interpreter, SQLite lifecycle and dependencies.
A separate Rust backend would add a second runtime boundary without replacing
the Python integration.

Each increment requires focused regressions and its owning repository gate;
the final integrated source requires the full gate and independent review.
Installed readback and a fresh confined lifecycle run establish adoption.
Existing live workers drain normally; installation alone does not establish
that their sessions loaded updated code or instructions.

## Recovery and rollback

No existing task is mass-rewritten or has its retry counters reset. New contract
fields are additive. Older cards retain their original interpretation. Release
journals retain file preimages and schedule identities; rollback uses the
existing fleet release operation, refuses intervening writers and never restores
board databases. Native adapter changes use source-checked maintained installers
and their private backups. Rollback must keep the reader for any new contracts
already created, or park those contracts until the compatible runtime returns.

Active monitor recurrence/sender repairs remain with their existing maintenance
owner. Integration consumes accepted source rather than creating a second fix.
