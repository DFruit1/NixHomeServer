# Capability recovery and reversible technical decisions

Owner decision, authenticated interactive session 2026-10-18: implement automatic
recovery and prefer informed, reversible technical decisions over asking the
owner to review source/copy conflicts they cannot usefully judge. Preserve
secrets, destructive-data and public-exposure approvals, truthful evidence,
independent acceptance and guarded activation. This policy supplies authority
for bounded remediation planning; it never bypasses a refused tool.

## Responsibilities and completion

The steward owns detection and follow-through. It observes all boards read-only
and requests coordinator action through the existing fixed-recipient queue. It
does not mutate cards, implement, delegate directly, install or deploy. The
coordinator owns the recovery outcome: use current native evidence, preserve the
existing feature/implementation owner and supply the missing input or capability.
Implementers implement; feature-reviewer independently accepts; project-auditor
owns substantive plan/provenance decisions, immutable amendments and FINDINGS.md.
An agent-supplied gap is a work assignment, not an owner approval question.

Self-healing is an execution duty (owner instruction 2026-10-22), not just a
reporting duty. Reconcile source copies, task/worktree bindings, input transfer,
maintained installer availability and stale procedural premises within existing
scope. Use `repair-task-workspace.py` and `hermes-workspace-repair.md` for a
parked task's exact checkout. Preserve old work and receipts, verify the actual
destination, deliver the real inputs, then resume through native lifecycle tools.
Never claim that creating a directory or naming a donor checkout delivered it.

The five-minute deterministic technical-recovery job commissions real native
head-coordinator workers independently of global idle. The coordinator may
inspect and amend parked technical cards with `kanban_amend` (exact version,
allowlisted fields, supersession evidence and readback), then resume through the
existing guarded lifecycle. For the amendment version, call the native tool
`kanban_amend({"task_id":"t_CARD"})` with `changes` and `expected_version`
omitted; its read-only response returns `version`. Pass that value as
`expected_version` in the next amendment call. There is no CLI version command
or task-table version column. The capability hold `recovery_version` is a
separate token inspected after the amendment. It does not edit active work, reset counters or
accept reviews. See the coordinator reference for the measured runtime and
assignee skill-catalog contracts. A current same-kind capability TRIAGE block loop
with no old supplier marker can use the closed terminal_episode supplier
clarification in that reference after actual input delivery is verified. It
only appends classification evidence; explicit or ambiguous old supplier text
refuses, every task field and review gate survives, and guarded resume remains
a separate operation with a fresh recovery token. An ordinary capability BLOCKED
hold has a separate closed clarification branch: latest finished blocked/blocked
run, its own latest run-bound blocked event, no current run or worker/lease,
exact reason/kind/recurrences/source_status payload, ready or review phase, and
positive integer recurrences matching the task below the native loop limit.
Use the same terminal_episode and changes exactly {block_kind:capability}, with
exact CAS, no old supplier marker of any kind, exactly one canonical agent or
model/provider supplier and substantive Repair evidence naming delivery actually
verified at the consumer. The coordinator attests to that evidence; the tool
does not accept it independently. Only one classification event is appended;
all rows, runs, links, historical events, phases, counters, checker/P1/P2
allowances and gates survive. Owner/external suppliers cannot be rewritten.
Read back the inspector's new supplier/version before any separately authorized
native guarded resume; breaker and iteration checks still apply. A blocked recovery handoff
owns its productive remedy; routine comments never cause duplicate recovery.
Repeated unchanged failed recovery attempts back off, then go once to
project-auditor.

An exact-source or tool-identity mismatch invalidates that attempt's old receipt;
it does not require endless preservation of an obsolete technical contract.
The coordinator may scope a reversible source/tooling correction or reconstruct
missing inputs, obtain independent acceptance, and record a bounded replacement
binding on the existing handoff. Preserve immutable historical plans and failed
evidence. Earn fresh checks at the selected source; never relabel historical
greens, silently change acceptance criteria, or export missing native identity.
Specific credential/destructive/exposure refusals and actual tool fences retain
their gates; use the supported reviewed one-shot mechanism for eligible fences.

## Delivering generated evidence

Use native attachment transfer when it can carry the complete bytes. If inline
base64 is truncated or a local URL is refused by SSRF protection, retain the
commissioned non-secret capsule and record its exact path, byte count, SHA256
and actual transfer failure on its card. Never reconstruct omitted bytes or
change network routes to evade the refusal.

The coordinator supplies the missing transfer through an already authorised
file-ingestion surface. An interactive coordinator/operator whose current rules
permit it can use `hermes --profile head-coordinator kanban --board BOARD attach
TASK FILE`. A refused worker/delegated child must not run that command, launch
an unscoped session or change context; report the gap through the existing
coordinator route. The recipient acts under its own current permissions, not
authority conferred by the request or supplied path.

Before ingestion, verify the owning card commissioned that exact output and
check its bytes against the producer's recorded identity. After ingestion,
verify the actual stored native attachment bytes, record its ID/hash and supply
readback before resuming the missing handoff. A summary path is not delivery.
Transfer-only recovery does not require repeating unchanged source work or
earned tests; preserve the candidate's independent review and activation gates.

## Conflicting copies and obsolete procedures

For non-secret source/configuration/document copies within authorised scope,
agents may choose a canonical copy without owner adjudication. Compare current
ownership, recorded approvals, source ancestry, actual contents and relevant
tests; newest filename or mtime alone is insufficient. Preserve both source
identities and retrievable bytes before replacement, using the existing private
content-addressed backups or retained disjoint worktrees. Record the selected
copy, concrete reason, affected consumers and exact rollback source/procedure on
the existing card. Bound the writer window and recheck inputs before replacing.
Preserve unrelated edits; never merge or reset an active worker's dirty tree.

Escalate a substantive source/provenance/architecture choice to project-auditor
with a finite question and alternatives. The coordinator records the resulting
decision; the auditor alone persists FINDINGS.md. Independent review checks the
actual chosen result. Reversible decisions may accept a small documented risk
without asking the owner to perform technical review. This does not authorise
destructive data choices, credential changes, wider exposure, new resource trades
or bypassing an actual tool fence.

When original source or a staging package is gone, select a current authorised
target and prepare a new durable package with new identities and fresh readiness
acceptance. State which historical claims remain unknown. A new reconstruction
cannot inherit old test/operation receipts. Do not demand output from missing
files or resurrect a retired candidate merely to clear a dependency. Keep
immutable historical plans intact; record supersession and any evidence-contract
amendment on the existing handoff. Generic old privacy/personal-terminal rules
follow current autonomy policy; specific physical/session/observation requirements
and genuine owner prohibitions still apply.

## Monitoring and deduplication

`python3 ~/.hermes/scripts/capability_recovery.py --inspect` is read-only. The
existing two-hour opportunity monitor includes stable CAPABILITY_HOLD lines for
parked capability episodes, including scheduled/triage/todo holds without a later
release and newly recorded scheduled agent-supplied waits. Preserve each wait's
actual wake conditions; observation never grants execution. Its fingerprint covers reason, runnable scope, relevant prerequisite
states, actual checkout commit/tree identity, attachment metadata and bounded allowlisted installed
helper hashes. These are wake signals, not proof an active session loaded a fix
or an artifact passed verification. It never reads credentials or executes tests.
Coverage errors fail visibly and never count as resolution.

For each newly added or changed line, the steward uses its exact key and version:

```text
python3 ~/.hermes/scripts/capability_recovery.py --handoff BOARD:TASK VERSION
```

The helper rechecks current evidence, refuses stale/incomplete observations and
queues a deterministic payload only to head-coordinator. IDs are per task/version;
one changed task never requeues every unchanged finding. Repeating the same
handoff is idempotent. Queue delivery remains distinct from completed recovery.
The existing four-hour stall job inspects unresolved outcomes with its existing
8h/16h/24h reminder backoff, including the same parked capability episodes and
material-input versions. Scheduled holds remain visible even when old reasons
omit a supplier marker; changes to related task states and actual verifier
verdicts/revisions wake the same hold. Preserve its time or acceptance condition.

do not duplicate that delivery with another queue call. Routine acknowledgments
