# Activation handoff verification

Use when a reviewed candidate overlaps dirty files in a checkout-backed runtime. This is a routing and evidence recipe, not an installation algorithm or authority to activate.

## Procedure

1. Read the whole-candidate verdict and existing paired decision with `kanban_show`. Separate product defects, missing execution evidence and unsafe adoption instructions. Retain independently accepted gates while routing only concrete remaining corrections; re-auditing unchanged passing slices adds cost without resolving the failed handoff.
2. Freeze full baseline/candidate identities and the accepted changed-file hashes. Record original dirty capture independently, including its bytes, provenance and preservation location. Require a permitted checksummed transfer into each consumer workspace before verification; a sibling path in a report is not usable evidence by itself. For append-only rehearsal attempts, require an explicit receipt-selection record naming the authoritative bundle and why earlier bundles are non-authoritative. Preserve earlier attempts and route the selected case-level receipts to the existing verifier; a final green suite or harness exit does not prove that earlier partial failures were recovered safely.
3. Route an isolated adoption-and-rollback fixture with separate assertions for the states below. Never accept a fixture that tests only preservation: keeping a dirty imported file unchanged can leave the rejected implementation active under the accepted HEAD.

| State | Required evidence |
|---|---|
| Before adoption | Baseline ref, index/staged state, dirty bytes and unrelated tracked/untracked/ignored state |
| After adoption | Exact candidate bytes in changed active product paths; original capture still independently recoverable; unrelated state preserved |
| After rollback | Original ref, active dirty bytes and index/staged state restored; unrelated state preserved; candidate-added paths handled without deleting owner changes |
| Refusal or interrupted step | Nonzero failure reported; no silent continuation; recoverable state demonstrated rather than assumed |

4. Require the implementer to check every mutation's exit, bind expected-old reference checks to the frozen revision validated at preflight, and exercise intermediate-failure recovery. Test the actual adoption and rollback plumbing after changing the ref between preflight and mutation; require refusal with no further state changes in both directions. Do not substitute a freshly read HEAD as expected-old: it accepts the intervening change and defeats the preflight guard. Include staged edits and untracked/ignored collisions at candidate-added paths. A final successful status comparison does not establish that an interrupted multi-step procedure is safe.
5. Model cumulative state after every interrupted stage and execute the literal published recovery instructions from each state. Assert restored ref, logical index/staged entries, captured active bytes, unrelated state and safe handling of candidate-added paths; distinguish logical index restoration from raw index-byte identity. Do not accept a successful helper as proof of the recovery table: different documented steps can leave the candidate ref active even when the helper restores it.
6. Send the changed handoff to feature-reviewer for independent execution and an active-byte identity assertion; return plan contradictions or newly required scope classification to project-auditor instead. Keep the existing readiness decision gated on that verification. If only evidence/instructions changed, verify those corrections without repeating the unchanged whole-source audit; if source changes, require a fresh changed-range review.
7. Carry accepted source readiness into the existing installation/handover owner only after a clean verdict. Keep installed and loaded identities, supervisor activation and phone acceptance as separate remaining receipts. Report the actual stage, not the task's done status.

## Reconcile installed identity drift

Use when a fresh installed-file receipt no longer matches the revision required by an existing live-acceptance card.

1. Read the completed identity check and its existing execution/verifier children with `kanban_show`. Compare the fresh installed digest and capture time with the earlier accepted identity receipt; retain successful authorization and pairing receipts independently. A new mismatch invalidates the old byte-identity evidence, not every successful check.
2. Hold the existing live-test card through the sanctioned lifecycle before it can execute. If automatic dispatch already claimed it, record the exact failed prerequisite and prohibit acceptance activity. Add the unresolved identity-disposition decision as a mandatory parent of both execution and final verification; a completed-but-failed inspection otherwise satisfies ordinary dependency gating.
3. Route one bounded provenance reconciliation using only public source and redacted prior receipts. Require the full installed digest, matching committed blob/revision if any, applicable source verdict, installation provenance and any later approval that supersedes the old pin. Keep private runtime inspection local; do not repeat the spent authorization check to answer a source-provenance question.
4. Distinguish the outcomes: later accepted and properly activated bytes may justify explicitly superseding the stale pin; unreviewed or altered bytes need a scoped repair/review plan; incomplete provenance remains UNKNOWN. A match to current master proves source correspondence only, not review or activation approval. A changed mtime orders captures but does not establish which actor changed the file.
5. Preserve current installed bytes while the disposition is pending. Do not blindly restore the older helper, because it may discard later authorized corrections. Do not widen acceptance to the newer digest merely to clear the mismatch. Carry any necessary restoration or adoption through its reviewed installation owner, with rollback and installed-byte receipts.
6. If the single reconciliation remains UNKNOWN because later acceptance receipts were not established, stop repeating historical receipt discovery. Return the exact accepted-to-installed source delta to the plan-owning auditor for a classified prospective acceptance procedure. Route independent exact-source/integration review, then a fresh local installed-hash/stat receipt and independent verification of that receipt. Keep this evidence-only procedure separate from source repair or installation authority; a rejection requires a separately assessed repair scope, not blind restoration. Preserve historical UNKNOWN rather than relabelling prospective acceptance as proof of earlier authorization.
7. Have the paired coordinator consume the actual source and installed-identity verdicts before explicitly adopting the new accepted identity and updating obsolete acceptance criteria. Read back the dependency edges and final hold/release status. Release only the identity blocker; real phone receipt, authenticated exact-card reply, comment-before-unblock and confirmation remain separate acceptance evidence.

Completion criterion: execution and verification use an explicitly accepted installed identity with recorded provenance. No phone test, rollback, reload or feature acceptance is authorized by provenance reconciliation alone.

## Recompose after the deployed baseline moves

1. Batch `kanban_show` for the completed whole-set review and paired decision, then inspect their existing children. Read the durable reviewer report before routing: a decision worker may already have created the corrective graph while the notification was in transit. Reuse that graph rather than commissioning another unchanged audit.
2. Carry the reviewer's full live commit, deployed-source hash and activation provenance into the decision. Distinguish standalone source acceptance from deployment safety: green gates on a diverged candidate do not authorize reverting intervening deployed changes. Keep the rejected range undeployable.
3. Return a contradiction with an immutable selected base to the plan-owning project-auditor for a classified integration addendum. Scope it to the exact already-deployed baseline plus the accepted incremental repairs, not moving master. Require recorded classification and exact carried approval scope; preserving deployed state is not retrospective approval of that state or permission to change an older recovery contract.
4. Route one bounded serial composition in an isolated durable worktree. Replay only the accepted increments in plan order into new local commits; prohibit rewriting accepted branches or merging the obsolete candidate's whole ancestry. Preserve unrelated deployed paths byte-for-byte. Stop on extra production conflicts or widened ownership for assessed correction, because conflict resolution can silently expand the approved change.
5. Route independent feature-reviewer verification of the actual base..new-HEAD range, with ancestry, owned-path inventory, protected-path equality, clean status and all required behavioral gates. Require case-level inventory of both regression sets at a test conflict: a stable test count cannot show that assertions survived. Account for superseded cases explicitly rather than treating absent names as automatically preserved or defective.
6. Gate accepted-only candidate freezing on the verifier's actual ACCEPT, not its done status. Preserve HEAD/tree identity and reconcile receipts without rerunning unchanged suites; changed bytes invalidate the source verdict. Keep the original coordinator handoff open and parent-gated on these actual completions, never make execution depend on that unfinished handoff.
7. Once the real frozen identity exists, create the fresh exact-range whole-set deploy review and paired decision together. Reconfirm live provenance; another moved baseline returns to assessed correction rather than chasing master. Retain independent runtime, installation and recovery prerequisites. Freeze the selected reviewed source and mutable inputs through test and switch; identify relevant writers across boards. Unrelated isolated work may continue. No all-board implementation freeze is required.

Completion criterion: the existing graph contains a verified exact candidate and a fresh whole-set verdict for the current deployed baseline. Source acceptance alone clears neither activation nor the feature's remaining live criteria.

## Reconcile runtime prerequisites with current intent

Use when an activation prerequisite relies on a configuration premise or limit that current evidence or the owner's correction contradicts.

1. Batch `kanban_show` for the assessment, the existing paired decision and the deployment/activation handoff. Read the latest owner correction before historical approval wording; identify the single current verification branch and preserve its dependency hold. Do not create another verifier or rollout because a completed assessment is followed by a notification.
2. Consume safe-field evidence from the verifier or preparation worker: exact profile path, selected configuration values, command exits and configuration provenance. Keep endpoint definitions, timeout leaves and per-model overrides distinct; an unset named timeout field does not prove its endpoint definition is absent. A missing general leaf and an already-present intended value require different remedies.
3. Have the verifier establish which resolved provider identifier indexes the timeout lookup, its override precedence and the active transport. Keep disk state and conditional resolver behavior separate from observed loaded runtime. Do not add a named key merely to match a plan when the resolver would never consult it; an inert compatibility key adds configuration without repairing readiness.
4. Consume the current applicability verdict once. If the immutable plan's stop conditions fire, keep that plan undispatchable and return the established facts to its plan-owning auditor through the existing decision. Carry the owner's corrected intent without another value-choice gate. Require a new immutable classified revision for the changed prerequisites; if the intended leaf already exists and is operative, prefer a zero-configuration-delta readiness plan rather than an unnecessary mutation card.
5. Require the revision to distinguish API request timeout, non-stream stale watchdog, streaming grace, queue-wait allowance and acceptance-driver wall-clock/run budget. Do not mechanically replace a number in every deadline: these bounds protect different stages, and a non-stream watchdog receipt does not establish streaming generation safety. Preserve separately authorized test counts and retry restrictions; request only genuinely new authority.
6. Keep loaded-code identity, actual timeout/transport evidence, installed adoption/rollback, service health, quiescence and original recovery closures explicit. Configuration reads and source inspection do not clear live readiness. Gate the existing handoff on the corrected plan and its executed verification, not on an assessment card merely reaching done.

## Reconcile bounded live-test allowances

Use when live readiness or recovery depends on a limited number of approved public exercises.

1. Read the exact approval assessments, immutable current plan, historical execution receipts and existing paired decision with `kanban_show`. Identify each separately authorized allocation; do not pool smoke, readiness and recovery runs or carry a consumed smoke allowance into a new purpose.
2. Delegate one read-only ledger reconciliation scoped to the relevant boards and approval interval. Require a row per allocation: authorized purpose, count, outer wall-clock ceiling, retry rule, actual exercise starts, stops/exits, consumption, remaining allowance and receipt citations. Allow UNKNOWN when execution evidence is incomplete; missing completion records alone do not prove non-use.
3. Distinguish worker lifecycle runs from the approved exercise itself. Crashed implementation workers, fixture suites, source reviews and configuration reads do not consume a public-generation allowance merely because their task names mention readiness. Conversely, an exercise that actually started must be accounted for even when its enclosing worker never completed.
4. Require positive evidence for an unused allocation: reconcile the authorized execution path with cross-board run records and explicit pending-exercise receipts. Report contradictory or uncovered paths as UNKNOWN rather than inferring unused capacity from a title search or absence of a driver card alone.
5. Inspect the returned command's role before routing execution. An approved fixture-gate runner and payload-free receipt schema are preparation evidence, not a public-run acceptance driver. Require the concrete bounded driver to enforce the approved whole-run ceiling and retry/count rules; route missing driver or changed transport/receipt scope through the existing auditor/decision chain without launching a trial run.
6. Carry the ledger into the existing paired decision without releasing runtime readiness. Preserve the intended worker-patience setting separately from the exercise ceiling; increasing patience does not enlarge test duration or replenish attempts. Retain loaded transport, client/deployed contract, installation, health and quiescence gates, because an unused allowance proves accounting—not operational safety.

Completion criterion: the existing decision has a cited allocation ledger and an explicitly identified driver/receipt disposition. No generation, transport change or deployment is authorized by ledger reconciliation alone.

## Deliver the currently authorized owner-terminal preflight

First apply the current owner-approved automation policy in hermes-autonomy.md.
A generic personally opened-terminal requirement is superseded by exact reviewed
bot execution after authenticated approval. Record the old clause and current
owner decision, obtain any necessary narrow evidence-contract addendum, and use
autonomy-policy.py. Never invent owner execution or remove guard markers. Keep
the personal procedure below only when its actual assertion depends on a physical
action, owner login session or firsthand observation; a guard refusal alone does
not prove that dependency. Missing/deleted scripts still need durable preparation
and fresh readiness review before any command is issued.


1. Resolve the requested decision label through the read-only owner inbox helper. Read the current blocking reason and the accepted delivery verdict; distinguish a request for commands from an approval or returned execution evidence.
2. Retrieve the authoritative reviewed command sheet or handoff, not its historical predecessor. Check its recorded digest against the actual artifact and verify the referenced script is present and readable without running it in an agent terminal. Artifact verification establishes delivery identity, not owner execution provenance.
3. Extract only the currently authorized read-only preflight. Lead with opening an independent terminal; show the exact issued interpreter, flags and script path, followed immediately by `printf 'Exit status: %s\n' "$?"`. Do not insert a pipe, intermediate command or environment override, because that can lose the producer exit or change the guarded execution context.
4. Ask for the actual permitted output and exit, with personal attestation statements confirmed only if true. Do not pre-fill assertions on the owner's behalf or treat absent agent markers as proof of independence. Keep stage creation, product tests and activation withheld until their distinct prerequisites pass.
5. Preserve any refusal unchanged for the existing verifier/decision; never suggest clearing markers or using a different execution principal to obtain a green result. Leave the gate blocked until returned evidence resolves its exact question.
6. If asked which message was sent and when, retrieve the exact prepared payload, originating request and transport receipt separately. Identify it by a recognizable opening or command and its intended channel. Convert only an evidenced timestamp into the owner's timezone and label it prepared, attempted or delivered; a preparation/comment timestamp is not a send timestamp. If delivery remains unproven, state that directly without asserting either arrival or non-arrival. A delivery record for a later blocker alert does not prove the earlier command message arrived.

## Accept native operator receipts

Use when a guarded operation requires an independently opened owner login terminal, while a worker may collect separate read-only runtime evidence.

1. Read the completed collector, its raw owner receipt and the existing verifier/paired decision through `kanban_show`. Preserve the existing graph; collection completion makes evidence available for review, not installation safe.
2. Separate provenance for each evidence component. Record native marker-presence evidence and the four-command exits as native; label worker-supplied path/hash resolution separately. A supplemental read-only binding can resolve a missing identity section without converting it into native execution proof. Do not request another owner run merely because one optional probe failed when the saved evidence already establishes an installation STOP.
3. Classify each required check from its own saved exit and output. Keep dry-run plan computation, check-mode DRIFT, source integrity and rendered-artifact freshness distinct. Treat an enclosing report helper's zero exit as report completion only when nested required checks failed. Forward fresh stale-render evidence to the existing verifier; a stable manifest digest or an earlier publication-minute pass does not negate current content drift. Never republish artifacts solely to obtain a green timestamp-sensitive check.
4. Bind the prospective scheduled command to its actual executable, interpreter and CLI/DB/parser module paths and hashes, then compare those bytes with the reviewed source. Treat missing required command support or mismatching modules as an installation STOP; repository HEAD, help output alone and a valid no-write receipt cannot establish safe adoption.
5. Post only the new acceptance implications on the existing verifier and read back that exact comment. Preserve valid native evidence, distinguish collector classifications from independent verdicts, and retain installation/activation holds through the paired decision. Reuse the bounded changed-composition review instead of rerunning settled source matrices or creating another receipt/adoption graph.

Operator handoff pitfall: describe actual filesystem effects separately from board-write counts; a verifier that temporarily rewrites and restores receipt files is not a no-filesystem-write operation, and calling those effects harmless requires reviewed preservation evidence.

## Evidence-specific pitfalls

- Verify rollback restores the baseline instead of trusting a zero exit: `git merge --ff-only <baseline>` may report already up to date while leaving the newer candidate active.
- Distinguish expected source hashes from active file hashes: `git rev-parse HEAD` proves a reference, not the bytes a checkout-backed runtime imports.
- Preserve failing test coverage as unresolved until the exact cases execute: setup errors are neither product failures nor passing tests. Reuse an approved confined test environment when available, retain guards, and publish interpreter provenance plus exact commands and exits. Do not turn a missing test dependency into a source repair or silently authorize installation.
- Keep independently executed results separate from transferred prior logs and overlapping suite totals; evidence relocation and a baseline interpreter smoke test do not establish candidate execution.
- Treat a reproduced handoff defect as bounded implementer rework, not a fresh owner-policy question. Escalate only new scope, irreversible effects or capability requirements that the current authorization does not cover.
