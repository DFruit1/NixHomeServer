Framing & Data Structures
Rev2, 16 November 2026. This section replaces the Rev1 text. It keeps every Rev1 decision, rewrites the rules in plainer language, and fills each item Rev1 left "to be frozen" with a concrete proposed value: addresses, byte layouts, CRC parameters, the commit protocol, payload schemas and recovery actions. These values are proposals for review. Nothing here is implemented in firmware yet; V2.1 has only a Handle_Wipe_MRAM stub.
The places where Rev2 changes something Rev1 said are listed in "Rev2 changes to review" below. Questions that need a team decision are listed at the end of the section.
Principles
MRAM is the primary record store. Every reading, event and settings change is appended to a ring of immutable records in MRAM. SD and MQTT are copies made from that ring.
Append only. A record is never edited once it is committed, including a Tail Lock record. State changes are new records or a new metadata checkpoint.
Reclaim only saved data. Space is reused only after a record has been saved to the SD card or acknowledged by the MQTT broker. One destination is enough.
Lock rather than overwrite. If the ring is full of unsaved records, logging stops (Tail Lock) until a save succeeds. Unsaved data is never overwritten automatically.
Everything is recoverable after a power cut at any instant. Configuration and ring state are kept in alternating A/B slots, and each record carries a sequence number and CRC, so boot can tell committed data from a torn write.

A byte count that only increases (uint32). It does not wrap when the physical ring wraps. Physical address = ring base + (position mod ring capacity).

Logical position where the next frame will be written.
tail
Logical position of the oldest frame still kept. Frames in [tail, head) are retained.
sd_saved_end, mqtt_saved_end
Each destination’s saved boundary: every frame before this position has been saved to that destination. "End" means exclusive: the position just after the last saved frame.
Saved / unsaved
A frame is saved when it lies before max(sd_saved_end, mqtt_saved_end). Unsaved bytes = head − max(sd_saved_end, mqtt_saved_end).
C, R, U
C = ring capacity (122,880 bytes). R = control reserve (512 bytes). U = usable capacity for ordinary records = C − R = 122,368 bytes.
Log instance, log_id
One continuous log. A new log_id starts after a format, wipe, factory reset, recovery rebuild, schema change or sequence rollover.
Settings generation (settings_gen)
A number that increases by 1 for every settings change. Readings record the generation used to produce them.
Anchor
A Type 1 reading that fixes the time base for the compact Type 0 readings that follow it.
Commit marker
A 4-byte value written last. A slot or frame without a valid marker is ignored.
Decisions confirmed in Rev1 (unchanged)
Item
Decision
Record identity
Every ring record carries a 32-bit sequence number: readings, events, settings fragments and flush records alike.
Record length
Every frame carries a one-byte payload length. Lengths are no longer looked up in a per-type table.
When full
Unsaved records are preserved and normal logging locks. A record can be reclaimed after verified SD persistence OR acknowledged MQTT delivery; both are not required.
Settings recovery
A/B settings slots. The previous valid configuration is kept until the new one is committed and verified. Types 3/4 record the new configuration for the data that follows.
SD formats
A lossless binary archive plus a human-readable CSV export. The CSV is derived from the binary and can be regenerated.
Rev2 changes to review
Change
Reason
Logical positions are uint32, not 64-bit.
Even logging every minute, 2³² bytes lasts over 400 years. uint32 is atomic on the Cortex-M0+ and matches the SD and MQTT headers. A new log starts long before rollover.
CRC-32 for settings, metadata, snapshots and containers (Rev1: CRC-16). Frames keep CRC-8.
Settings slots are up to 2 KiB, where CRC-16 is weak. The STM32G070 CRC unit computes CRC-32 in hardware, and the server can use the standard zlib function.
Frame commit: the two magic bytes are written last.
This makes the commit point a single 2-byte write. A frame torn by a power cut has no magic bytes and is ignored.
The control reserve holds only the Tail Lock record (512 bytes).
Unlocking frees space before any further records are written, so no other record needs reserved space. Settings context reaches the server through cfg/applied, and reaches SD through each segment header, so snapshots never have to be re-appended.
Eight new record types, 14–21.
Log start, clock set, data gap, sensor fault, power critical, storage warning, tail unlocked and tilt reading. Rev1 listed these as missing; the event list on page 21 needs them.
Lazy reclaim in steps of at least 1 KiB.
Saved data stays in MRAM as long as possible, so it can be resent. Larger steps keep metadata writes infrequent.
Settings are encoded as tag-length-value (TLV) with stated bounds.
Fixes Rev1 inconsistencies (GPS alarm 0–8 vs 10, the missing Partial_Update setting), removes free-fall and gives the sensitivities linear scales. Documents the level formula.
Timestamps are uint32 UTC seconds since 1970-01-01.
The format is familiar to the server, valid until 2106, and paired with an explicit validity flag.

Question

Alarm hysteresis
A distance above or below the alarm level. After an alarm, the level must cross back past it before the alarm ends and can trigger again.
GPS and tilt frequency
Separate settings with the same options. Default: one reading of each at every send. Each can instead be N readings per send interval, a fixed interval in seconds, or off.
Accelerometer
Free-fall detection removed. Tap monitoring can be switched on or off. Tilt angles are read on their own schedule (default: every send).
Sensitivities
Linear 1–10 scales: tap threshold (11 − value) × 0.75 g; GPS alarm distance (11 − value) × 25 m.
Battery pack
Two 21700 cells in series (2S, 7.4 V nominal). Critical limit 6.60 V, recovered above 7.00 V.
Battery and solar alerts
Raised by the server from state/health and test data. The logger has fixed firmware limits for critical battery levels only (Type 18). Water-level alarms stay on the logger.
Wipe with unsaved data
Allowed, with a second confirmation that echoes the unsaved count, on top of the nonce handshake.
MQTT message size
Up to 1,500 bytes per data/stream message using AT+QMTPUBEX (binary-safe), subject to a bench check.
Hardware constraints (PCB V1.08)
Item
Constraint
Device
U5 = Everspin MR25H10CDF: 1 Mbit (128 KiB), 2.7–3.6 V, SPI up to 40 MHz, no write delay, unlimited write endurance. The schematic symbol says MR25H40, but the BOM and value say MR25H10; this map assumes 128 KiB.
Bus
CS PB13, MISO PB6 (AF4), MOSI PB7 (AF1), SCK PB8 (AF1). This is SPI2, which the SD card also uses (on PA0/PC2/PC3). The firmware must switch SPI2’s pins between the two devices. 10 kΩ pull-ups on CS, MISO, MOSI and SCK; WP and HOLD are tied high.
Start-up
Wait at least tPU = 400 µs after power-up before the first command.
Low power
Send SLEEP (B9h) between uses: about 7 µA, against 90–115 µA in standby. Wake with ABh. Do not idle SCK low against its pull-up (about 330 µA): use SPI mode 3, or set the pins to inputs when idle.
Power loss
The STM32G070 has no guaranteed brown-out or PVD warning, so writes can be torn at any byte. Every structure below is designed for that.
Address wrap
The chip wraps at the end of its whole array, not at the end of Zone 5. A ring access that crosses the end of Zone 5 must be split into two operations by the firmware.
Encoding conventions
Multi-byte integers are little-endian. Integers are unsigned unless shown as i8/i16/i32. f32 is IEEE-754 single precision.
Native C structs are never written directly: each field is serialised at the offsets given, so padding cannot change the layout.
Time is uint32 seconds. When the time-valid flag is set, it is UTC seconds since 1970-01-01. When the flag is clear, it is seconds since this boot. Local time is used only on the display.
Not available: 0xFFFF for u16 readings, INT32_MIN for i32 values, INT16_MIN for i16, NaN for f32 settings.
Reserved fields and bits are written as 0 and ignored when read.

Zones 0 & 1 — settings slots (A/B)
Each slot holds one complete configuration. The slot written most recently and verified is active; the other is the rollback copy. A change always overwrites the older slot, so the active slot is never touched during a change.

A slot is eligible if its magic, layout version, length bound, CRC and commit marker are all valid and every setting passes the range checks below. A setting with a valid CRC but out of range makes the slot ineligible. At boot the eligible slot with the higher settings_gen is used. Generations are plain uint32 counters compared as integers; they will not wrap in practice, and firmware refuses changes above 0xFFFFFFF0.
Applying a settings change
1.Validate the complete requested configuration in RAM. Assign generation = settings_gen_reserved + 1, record it in a metadata checkpoint, then build the TLV payload. A generation is never reused, even if this change later fails. Check that the ring has ordinary space for both snapshot sets (Types 3 and 4) without touching the reserve. If the logger is tail-locked or short of space, reject the change and report "not applied" on cfg/applied.
2.Write the candidate to the older slot. First write 0 to its commit marker and read the marker back. Then write the header, payload and CRC. Read the whole slot back and check its CRC.
3.Append the snapshots: the Type 3 set, then the Type 4 set, each verified (see "Settings snapshots"). The old settings are still active at this point, so readings taken now still use the old generation.
4.Commit: write the commit marker, read it back, and re-check the slot. Only then activate the new settings, append an anchor reading (Type 1, reason 3) carrying the new generation, checkpoint the metadata and publish cfg/applied as successful.
If power is lost before step 4 completes, the old slot is still the newest eligible slot, so the old settings remain in force. Snapshots left by the interrupted change are harmless: a snapshot never proves activation; the anchor does. If power is lost after step 4, boot finds the new slot committed and finishes the activation (see "Boot").
Rollback: if new settings fail a runtime health check, the previous configuration is re-applied through the same four steps as a new generation (source 3). Old generations and old ring records are never altered. Both slots are never updated in one change.
Settings encoding (TLV)
The payload is a list of entries: tag (u8), length (u8), value. Tags appear in ascending order, each at most once. A missing tag means the default. Unknown tags are preserved and ignored, so older firmware can read newer settings. Strings are UTF-8 with no terminator.

Writing a checkpoint
Write to the older slot: (1) write 0 to its commit marker; (2) write bytes 0–79 with metadata_seq one higher than the newest slot; (3) read back and check the CRC; (4) write the commit marker and read it back. A torn write can only damage the slot being written, so the newest committed checkpoint always survives.
A checkpoint is required: before any sequence number at or above seq_reserved_end is used; after tail advances and before the head writes into the freed space; after either saved boundary moves; when the lock or recovery state changes; and before sleeping if anything changed since the last checkpoint. Head does not need a checkpoint after every frame, because boot scans forward from the stored head.
Invariants checked at boot: tail ≤ head; head − tail ≤ C; sd_saved_end ≤ head; mqtt_saved_end ≤ head; tail ≤ max(sd_saved_end, mqtt_saved_end); last_seq < seq_reserved_end; active_settings_gen ≤ settings_gen_reserved. A checkpoint that fails any invariant is not eligible.
Zone 5 — the ring
Logical position x is stored at physical address 0x02000 + (x mod 122,880). Head, tail and both saved boundaries always fall on frame boundaries. A frame may cross the physical end of the zone; it is then read or written in two operations.

Sequence numbers and log identity
Each log starts at sequence 1. Every frame takes the next number, whatever its type, across physical wraps. Numbers order frames; they are not sample counters or timestamps.
Numbers are reserved 64 at a time: before using a number at or above seq_reserved_end, the firmware raises seq_reserved_end by 64 and writes a checkpoint. At boot, numbering resumes at seq_reserved_end, so a number that might have been used before a reset is never reused. Up to 63 numbers can be skipped per reboot; that is harmless.
Before next_seq reaches 0xFFFFF000, a new log is started (Type 14, reason 4).
log_id is a uint32. A new log_id is max(previous log_id + 1, current UTC seconds) when the clock is valid, or previous + 1 when it is not. If no previous log_id is known and the clock is invalid, it is 0x80000000 OR the low 31 bits of a CRC-32 over the MCU UID and 16 ADC noise samples.
Records are uniquely identified by (DEVICEHEX, log_id, sequence). Every SD segment and MQTT batch carries log_id; DEVICEHEX comes from the topic, and the SD header carries the raw MCU UID.
Appending a frame (commit protocol)
1.Build the frame in RAM with bytes 0–1 set to 0x00 0x00, and compute the CRC-8.
2.Check space. An ordinary frame needs (head + size) − tail ≤ U. If it does not fit, reclaim saved space (see "Persistence"); if that is not possible, enter Tail Lock.
3.Write the whole frame at the physical address of head, splitting it at the end of Zone 5 if necessary.
4.Read it back and compare. On a mismatch, rewrite once; a second mismatch is an MRAM fault (see "Faults").
5.Write 0xA5 0x5A to bytes 0–1. This is the commit point.
6.In RAM: head += size; last_seq = sequence; next_seq += 1.
If power is lost before step 5, the frame has no magic bytes and boot ignores it. Old frames from the previous lap that lie beyond head are rejected because their sequence numbers are lower than last_seq.
Finding head at boot (forward scan)
Start at the checkpoint’s head and last_seq. Accept the frame at the current position only if: the magic is A5 5A; the type is not 255; last_seq < sequence < seq_reserved_end; the CRC-8 matches; and the frame ends within tail + C. If it is accepted, move past it and repeat. The first frame that fails ends the scan, and that position becomes head. The scan never goes further than tail + C.

Time, anchors and readings
An anchor is a Type 1 reading with the ANCHOR flag. It is sample 0 of a run of routine readings. A Type 0 reading with sample_index k was scheduled at anchor time + k × interval_s. A missed reading leaves a gap in the index, so it is never confused with a shorter interval.
A new anchor is written: at the start of a log; after every boot; when new settings take effect; after a clock set that moves the schedule; after an unlock; when the schedule starts or is realigned; and before sample_index would exceed 65,535.
Readings carry their settings generation, directly or through their anchor. A snapshot appended without activation never changes how readings are interpreted.
When the RTC is not valid, times are seconds since boot with VALID = 0. Reset-default dates such as 2000-01-01 are never presented as real times. When the clock is later set, a Type 15 record pairs uptime with UTC, so the server can convert this boot’s relative times. No timestamp is invented across a power loss.
An alarm triggered by a scheduled reading produces the Type 0 reading, then the Type 8/9 event, then a Type 1 reading (reason 16) with the same value.
Accelerometer. When tap detection is on, the ADXL345 runs in full-resolution ±16 g mode with its tap interrupt armed: THRESH_TAP = (11 − sensitivity) × 12 (62.5 mg per count) and a fixed 10 ms duration (DUR = 16). Free-fall detection is not used. Tilt is measured on its own schedule by averaging 16 samples; pitch and roll are computed from the gravity vector. The reference orientation is the tilt at the last test or on first deployment, and a change of more than 10° from it raises the orientation alarm (Type 12).
GPS alarm. Only a 3D fix with HDOP ≤ 2.5 is compared with the reference position (the first such fix after a test or deployment). A distance above (11 − sensitivity) × 25 m raises Type 10.
Alarm hysteresis. A high alarm starts (Type 8) when the level rises above Maximum GWL Alarm. It ends (Type 9) only when the level falls below Maximum GWL Alarm − Maximum GWL Hysteresis, and only then can it start again. The low alarm mirrors this: it starts below Minimum GWL Alarm and ends above Minimum GWL Alarm + Minimum GWL Hysteresis. A level hovering around an alarm value therefore produces one alarm, not a stream of them. Water-level alarms are always raised by the logger itself.
Settings snapshots (Types 3 and 4)
A snapshot is the exact TLV payload of the new settings slot. It is split into fragments of up to 241 data bytes; a typical snapshot fits in one fragment, and the 1,024-byte maximum needs 5.
Every fragment carries the generation, schema, its index and the fragment count, the total length, and a CRC-32 of the whole assembled snapshot.
All Type 3 fragments are written first, then a complete second set as Type 4. Each fragment is a normal frame with its own sequence number and CRC-8.
A set is complete when every index from 0 to count − 1 is present exactly once (or duplicated with identical content) and the assembled CRC-32 matches. If the Type 3 set is incomplete, the Type 4 set is used.
Persistence, reclaim and capacity
Saving (flush) to a destination
1.At the start, record end = head; the flush covers [start, end). start is the destination’s saved_end, or tail if saved_end is below tail. In that case that destination has permanently missed [saved_end, tail) from MRAM; the batch or segment is flagged so the gap is visible.
2.Transfer the range (see SD output and MQTT). Frames appended during the transfer wait for the next flush.
3.When the destination confirms a prefix of the range, move its saved_end to the end of that prefix and write a checkpoint. A partial save keeps the remainder unsaved.
4.Append a Type 6 or Type 7 record. That record lies outside the range it confirms. It is carried by the next flush; no extra flush is started just to deliver it.
SD is attempted first when both are available. A missing or failed SD card never blocks MQTT. A save to one destination says nothing about the other: if data is reclaimed after an MQTT-only save, the logger never claims an SD copy exists. A retry after an uncertain acknowledgement may resend the same frames with the same identities; the server removes duplicates.
Reclaiming space
Tail may advance only up to max(sd_saved_end, mqtt_saved_end), and only over whole frames. Reclaim is lazy: tail moves only when an ordinary frame does not fit, and then by at least 1 KiB, or by all reclaimable space if that is less. The new tail is checkpointed before head writes into the freed bytes.
Almost full
When unsaved bytes reach 75% of U, append Type 19 (kind 1), publish EVENT_MRAM_ALMOST_FULL at the next connection, and bring the next connection forward to the next wake. The warning clears (Type 19 kind 2) when unsaved bytes fall below 50% of U.

Tail Lock
Entering the lock
If an ordinary frame does not fit and no saved space can be reclaimed, the logger appends a Type 13 record using the control reserve, sets TAIL_LOCKED and lock_start_time, and writes a checkpoint. The reserve exists only so this record can always be written. Because the lock is entered while 512 bytes are still free, it never depends on the last free bytes.
While locked
No ring appends, and nothing is overwritten.
Readings and alarms still run: the display updates, and alarms and the lock itself are published to the event topic when connected. They are not stored; missed_readings and missed_events count them in the metadata. Any RAM queue is temporary and lost on power loss.
Save attempts continue: SD at every wake if a card is present, and an MQTT connection at the next wake and then every min(send interval, 6 h).
Settings changes are rejected as "not applied (locked)".
Leaving the lock
The lock ends when, after a save, unsaved bytes are at most 50% of U. Normally one save clears everything.
1.Write a checkpoint with the new saved boundary.
2.Advance tail over the saved data and write a checkpoint. There is now ordinary free space.
3.Append Type 6 or 7, Type 20 (tail unlocked), Type 16 (data gap: from lock start to now, with the missed counts) and an anchor reading (Type 1, reason 5).
4.Clear TAIL_LOCKED and the missed counters, and write a checkpoint. Routine logging resumes.
If power is lost during unlocking, boot still sees TAIL_LOCKED and repeats from step 1. Repeated records are harmless. The Type 13 record is never modified, and there is no "unlock override": only a successful save, or a deliberate WIPE_MRAM, ends a lock.
SPI2 sharing and timing
Only one task owns SPI2 at a time. On each hand-over the firmware switches the pin functions and the SPI mode: MRAM uses mode 3 (SCK idles high, matching its pull-up); the SD card uses mode 0.
SD work runs in units of one 512-byte sector write, each with a 250 ms timeout, and releases the bus between units. An MRAM append (about 1 ms at 4 MHz for the largest frame, including the read-back) can therefore run between units.
Target: a scheduled reading is taken within 2 s of its scheduled time, because Type 0 times are derived from the schedule. MQTT transfers and CSV conversion also yield to readings and MRAM writes. Rev0 asked for zero blocking; Rev2 sets these measurable limits instead.
SD output
The binary archive is the lossless, authoritative copy. The CSV is derived from it for people to read. Both are on the same card, so together they are one backup, not two.

Writing and verifying
Append whole frames only, in chunks of up to 4 KiB. After each chunk, call f_sync, then read the bytes back and compare them with MRAM.
Only when the whole flush range has been written and verified does sd_saved_end move (followed by a checkpoint and a Type 6 record).
On restart, walk the last segment from header_len, accepting frames with valid magic, CRC-8 and increasing sequence. Truncate the file after the last valid frame. If the header itself is invalid, rename the file to .BAD and start a new segment. Partial bytes never count as saved, and a retry is never appended behind a torn frame.
If /GWL/<LOGID>/ is missing, or the last segment does not end where sd_saved_end expects, the card is new or different: start a new segment at tail, so it receives everything MRAM still holds. sd_saved_end never moves backwards.

MQTT data/stream
Each message on <ROOT>/<DEVICEHEX>/data/stream (QoS 1, not retained) is one binary batch: a 32-byte header, up to 1,464 bytes of whole frames, and a CRC-32 over everything before it, so a message is at most 1,500 bytes. A frame is never split across batches.
Publish command. Batches are sent with AT+QMTPUBEX=<client>,<msgID>,1,0,"<topic>",<length>. The EC21 then reads exactly <length> bytes, so any byte value can be sent; 1,500 bytes per message is the module’s limit in this mode. The V2.1 firmware uses AT+QMTPUB instead, which ends the message at a Ctrl-Z byte (0x1A) and treats ESC (0x1B) as cancel. That suits JSON text, but binary frames contain those byte values, so data/stream must use AT+QMTPUBEX. The JSON topics can stay as they are.

Boot
1.Wait at least 400 µs after power-up, send WAKE (ABh) and set SPI2 to MRAM mode.
2.Read Zones 0–3. If no zone contains a recognised magic value ("GWS1" or "GWM1"), the chip is blank: format it (see the table below) and stop here.
3.Choose the eligible settings slot and metadata slot with the highest generations. Report any slot that failed a check.
4.Run the forward scan from the checkpoint head to find the real head and last_seq.
5.Set next_seq = seq_reserved_end, reserve a new block of 64, add 1 to boot_count, and write a checkpoint.
6.Reconcile settings. If the selected slot’s generation is newer than active_settings_gen, the change was committed but not yet activated: activate it now (anchor, reason 3). If it is older, the newer slot was lost: keep the selected settings and report a rollback.
7.If TAIL_LOCKED is set, stay locked and follow "Leaving the lock" after the next successful save.
8.Otherwise, if the clock is valid and more than 1.5 sensor intervals have passed since the last record, append a Type 16 record (reason 2). Then append an anchor (reason 2) with a fresh reading and resume the schedule.
Faults and recovery
Condition
Action
Blank chip: no recognised magic in Zones 0–3
Format: default settings as generation 1 in slot A (source 1); metadata in slot A with head = tail = both boundaries = 0; Zone 4 zeroed; Type 14 (reason 1); anchor.
One slot of a pair invalid
Use the other slot and report it. The next write goes to the invalid slot anyway, because it counts as the older one.
Both settings slots invalid, metadata valid
Search the ring for a complete Type 3 or Type 4 snapshot of active_settings_gen. If one is found, rewrite it into a slot (source 5) and continue. Otherwise stop ordinary logging, enter RECOVERY, read the retained cfg/desired and apply it as a new generation.
Both metadata slots invalid, or invariants fail
Enter RECOVERY in read-only mode: report the problem, do not append and do not format. An operator then sends RECOVER_MRAM or WIPE_MRAM (below).
Frame CRC failure inside [tail, head)
Copy the bytes unchanged to SD and MQTT and report the sequence context. Decoders resynchronise at the next frame with valid magic, CRC and the next expected sequence. A historical record is never rewritten.
Read-back mismatch twice on one write
MRAM fault: stop appends, set last_error, report on state/debug and event. The display, alarms and MQTT continue.
SD missing or failing
Keep logging to MRAM. Append Type 19 when the state changes. MQTT saves continue.
Format, wipe and reset scope
Operation
Scope
Automatic format
Only for a blank chip, as above. Never for a corrupt or ambiguous chip.
WIPE_MRAM (cmd/danger)
Two-step nonce handshake. If unsaved data exists, the logger’s challenge reply also states the number of unsaved records and bytes, and the confirming command must echo that exact count as confirm_unsaved. A count that no longer matches (more data has been logged since) is refused, so an operator always confirms the loss they were shown. Keeps the settings slots. Zeroes the metadata zones and the ring and starts a new log_id. Then writes Type 14 (reason 2), Type 16 (reason 5, with the wiped counts) if unsaved data was lost, and an anchor.
FACTORY_RESET (cmd/danger)
As WIPE_MRAM, and also writes firmware defaults as a new generation (settings_gen_reserved + 1, source 4). Type 14 reason 3. Network keys are outside MRAM and are not touched.
RECOVER_MRAM (cmd/danger, new)
Rebuilds the ring from RECOVERY: scan for valid frames, take the highest-sequence unbroken chain as [tail, head), mark all of it unsaved so it is sent again, and start a new log_id (Type 14, reason 5) for new records. Recovered frames are flagged as resends.
WIPE_SD (cmd/danger)
Deletes /GWL/ on the card only. MRAM and sd_saved_end are unchanged. The acknowledgement warns that data reclaimed after an SD-only save is now gone.
Schema identity
envelope_version (u8) identifies the frame format: 1 = the format in this section. Rev0 framing was never implemented, so no Rev0 data exists to decode.
payload_schema (u16) starts at 1 and is raised by hand whenever any payload layout or meaning changes. A host test hashes the schema table and fails if the table changes without a version bump. This replaces Rev0’s compile-time hash, which changed on every rebuild.
A firmware update that changes payload_schema starts a new log (Type 14, reason 6), so one log never mixes schemas. Log start records, SD headers and MQTT batches all carry the schema, and the server keeps a decoder for every version.

FAQ
What replaces type_lengths[64]?
The length byte in every frame. A per-type table may still be used to check that a payload has the expected size, but it is never needed to find the next frame.
Which bytes does each CRC cover?
Frame CRC-8: type, length, sequence and payload (bytes 2 to 7 + L), not the magic bytes or itself. Slot CRC-32: the slot header and payload up to the CRC field, not the CRC or the commit marker. Snapshot CRC-32: the assembled TLV payload. SD and MQTT CRC-32: everything before the CRC field.
Why both A/B slots and Type 3/4 snapshots?
The slots let the logger fall back to a previous configuration after a failed or interrupted change. The snapshots keep a record in the log itself of how every stretch of readings must be interpreted. They solve different problems; neither replaces the other.
Topic Structure
The topic structure for the loggers should be as follows
<ROOT>/<DEVICEHEX>/<TOPIC>/<SUBTOPIC>
ROOT: Fixed, root topic namespace (e.g. loggers). Allows for namespacing, such as production versus test environment. Not intended for namespacing things like projects, tenants or locations.
DEVICEHEX: A 24-character hex hash of the MCU UID. Used to uniquely identify the logger. The hash needs to be able to be derived by the logger itself using only the MCU UID to allow regeneration of its own ID if required and avoid losing communication in the field.
TOPIC: Different topic categories which are sorted as follows:
state: current state of the device. Retained messages, QoS 1.
event: publish events as they happen. Not retained, QoS 1.
data: stream for the logger to send raw data to from the ring buffer. Not retained, QoS 1.
cmd: send commands to the logger. Not retained, QoS 1.
cfg: topic for changing logger settings and logger acknowledgement of updated settings. Retained messages, QoS 1.
All topics shall initially be QoS1, with consideration for QoS 0 or 2 if needed.
MQTT broker must be configured with persistance enabled.
SUBTOPIC: optional sub-topics to signal different categories.
